## 2. 单模型结果

下表统一使用复核后的 N=241 Test。Base 使用 token 约束的二选一解码，LoRA 使用生成式 JSON；所有结果的 schema 合法率均为 100%，但 Base 的合法率由解码约束保证，只作为格式归一化参考。

阶段结论：

1. 所有 LoRA 均显著优于格式受控 Base，说明收益不只是 JSON 格式改善。
2. E5-975 的 Accuracy 和 F1 最高，FPR 低于 10%，适合作为默认平衡型单模型。

## 3. 多模型投票结果

候选模型为 E1-1248、E2-1248、E5-780 和 E5-975。融合规则只在 Dev 上选择并冻结：四个模型中至少两个投 BAD，则最终判为 BAD。

| 数据 | TP | FN | FP | TN | Recall | FPR | Accuracy | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 修正版 Dev（规则选择） | 45 | 13 | 18 | 124 | 77.59% | 12.68% | 84.50% | 74.38% |
| 复核 Test N=241（探索性） | 48 | 18 | 24 | 151 | 72.73% | 13.71% | 82.57% | 69.57% |

与 E5-975 相比，投票在 Test 上将 Recall 提高 6.06 个百分点，FPR 增加 4.00 个百分点，Accuracy 降低 1.25 个百分点，F1 提高 0.28 个百分点。与 E5-780 相比，投票牺牲 1.51 个百分点 Recall，但将 FPR 降低 6.86 个百分点。

因此，四模型二票规则适合作为召回与误报之间的折中候选，并达到项目 Go 标准；但它没有达到挑战目标。由于该 Test 已被观察并参与定向复核，这一投票结果只能标记为探索性结果，正式采用前需要在新增盲测集上确认。

## 4. LoRA 合并与推理速度对比

### 合并等价性

E5-975 LoRA 已合并为完整 Qwen3.5-27B 模型：12 个权重文件、54,713,606,768 bytes，合并耗时 124.97 秒。使用完全相同的 Swift Transformers 协议重跑原始适配器和合并模型，结果为：

- 两者 TP/FN/FP/TN 均为 44/22/17/158，所有二分类指标完全相同；
- 图片级决策一致 241/241（100%）；
- 完整响应完全一致 238/241（98.76%）；
- 3 条完整 JSON 文本存在差异，但没有改变 GOOD/BAD 决策。

因此，LoRA 合并不会损失本任务的图片级二分类能力，可以使用合并模型进入推理加速流程。

### Transformers 与原生 vLLM 实测

测速条件：同一合并模型、同一 GPU、同一批 241 张图片，顺序执行；vLLM `max_num_seqs=8`。这里的单图时间是批量任务的平均吞吐耗时，不等同于单请求在线延迟。

| 指标 | Transformers | vLLM | 对比 |
|---|---:|---:|---:|
| 图像推理总时间 | 380.94 秒 | 104.64 秒 | vLLM **3.64×** |
| 纯生成时间 | 356.15 秒 | 92.03 秒 | vLLM 约 3.87× |
| 平均单图耗时 | 1.581 秒 | 0.434 秒 | 减少 72.5% |
| 吞吐量 | 0.633 图/秒 | 2.303 图/秒 | vLLM 3.64× |
| 含冷启动总时间 | 411.03 秒 | 405.68 秒 | 约 1.01× |
| Schema 合法率 | 100% | 100% | 一致 |

vLLM 模型加载和编译耗时约 301.04 秒，导致一次性小批量任务的冷启动收益不明显；模型常驻后，稳态吞吐优势明显。按本次实测，冷启动盈亏平衡点约为 236 张图片。

原生基准中，合并 Transformers 与 vLLM 的决策一致率为 231/241（95.85%），vLLM 相比该 Transformers 口径 Recall 相同、FPR 高 1.14 个百分点、Accuracy 低 0.83 个百分点、F1 低 1.05 个百分点。另一方面，原生基准使用的冻结 prompt/图像预处理与正式 Swift 协议仍有差异；正式 Swift 协议已经证明适配器与合并模型 100% 决策一致。因此当前可以确认“合并安全”和“vLLM 吞吐加速有效”，但在生产切换前仍需完成 Swift 正式协议与目标 vLLM 服务协议的最终对齐验收。

## 5. 1 万、5 万、10 万组数据推理方案

### 时长估算

下表按本次单卡 A100 80GB 实测线性外推，包含一次模型加载；假设图片尺寸、输出长度和存储性能与本次 Test 接近。它是容量规划值，不是 SLA 承诺。

| 数据量 | Transformers 单卡 | vLLM 单卡 | 单卡预计节省 | 建议资源 | vLLM 建议墙钟时间 |
|---:|---:|---:|---:|---|---:|
| 1 万 | 约 4.40 小时 | 约 1.29 小时 | 约 3.11 小时 | 1×A100 | 约 1.3 小时 |
| 5 万 | 约 21.97 小时 | 约 6.11 小时 | 约 15.85 小时 | 2×A100 数据分片 | 约 3.1 小时 |
| 10 万 | 约 43.93 小时 | 约 12.14 小时 | 约 31.78 小时 | 4×A100 数据分片 | 约 3.1 小时 |

多卡方案采用多个独立单卡 vLLM 实例做数据并行，不采用单模型 tensor parallel：每张 A100 各加载一份合并模型，输入清单按图片唯一 ID 均匀分片，最后合并结果。这样实现简单，也避免跨卡通信降低吞吐。

### 上线前验收

1. 从目标大批量数据中随机抽取 500 张，使用正式 Swift Transformers 与目标 vLLM 服务双跑。
2. 要求 schema 合法率 100%、图片级决策一致率至少 99%；如有人工 Gold，要求 Recall/FPR 差异均不超过 1 个百分点。
3. 若未达到门槛，暂时使用已验证等价的 Swift Transformers，或在克隆环境中安装 ms-swift 并继续对齐模板和图像预处理；不修改当前健康的 `vllm_qwen35` 环境。

### 批量执行与审计

- 先生成只读输入 manifest，记录图片唯一 ID、绝对路径、文件哈希和分片编号；重复 ID 不重复推理。
- 每 1,000 张作为一个可恢复分片，输出独立 JSONL、运行日志、耗时和 SHA256；失败分片单独重试，不重跑全量。
- 模型启动后保持常驻，避免每个分片重复支付约 5 分钟 vLLM 加载/编译成本。
- 汇总阶段检查总行数、唯一图片数、缺失/重复记录、JSON/schema 合法率、GOOD/BAD 分布和异常退出。
- 保存模型路径、模型/数据哈希、vLLM/torch/transformers 版本、GPU 型号、随机种子和推理参数，保证结果可追溯。

如果使用四模型投票，每张图片需要运行四个模型，总计算量约为单模型的 4 倍。4×A100 最适合“一卡一个模型并行跑同一批数据”，此时墙钟时间接近单模型单卡时间：1 万约 1.3 小时、5 万约 6.1 小时、10 万约 12.1 小时，另加结果投票与汇总时间。默认大批量方案优先使用 E5-975 单模型；只有业务明确要求提高 Recall，且能接受额外成本时，才使用 E5-780 或四模型投票。

## 6. 阶段结论

1. 新 Test 经复核后形成 N=241 条件修正版；9 张虚拟/编辑或带水印图片因超出任务边界被排除。
2. E5-975 是当前最佳平衡型单模型，E5-780 是召回优先模型；四模型二票投票是探索性折中方案。
3. LoRA 合并在正式 Swift 协议下保持 100% 图片级决策一致，可以安全用于部署准备。
4. vLLM 稳态批量吞吐约提升 3.64 倍，但冷启动约 5 分钟，且生产协议仍需通过 500 张双跑验收。
5. 大规模推理优先采用“合并模型 + 单卡 vLLM 实例 + 数据分片 + 断点续跑”；在协议验收未通过前，不以速度为由替换已验证的 Transformers 正式口径。
